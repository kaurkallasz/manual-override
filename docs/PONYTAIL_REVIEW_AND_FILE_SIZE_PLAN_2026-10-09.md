What this repo does: This workspace runs a physical and virtual tower-defence game. One Flask hub hosts Gamemaster, Green and Purple modules; Photon owns the simulation, browsers display and submit commands, and a relay controls the robot arms. The workspace also contains ESP firmware, map and artwork tools, CAD scripts and test fixtures.

Assumed load: one game host, two players, one operator, two arms and their cameras/Atoms, with some additional browser views. This review does not assume multiple independent server workers or large public multiplayer traffic.

The recommendation is to fix authentication and persistence risks first, remove redundant code next, and then split the remaining large files by responsibility. Use 1,000 lines as a ceiling for maintained source, with an 800-line warning; smaller cohesive files should stay small. Implementation is proposed for approval. Only this report and the file inventory were added.

**Must fix**

1. **Current authentication credentials are committed to Git.** What this is: [hub-config.json](</Users/kaur/Documents/ChatGPT/Tower defence/manual-override/hub-config.json:3>) contains the cookie-signing secret and sandbox passwords. Problem: the file is tracked, and the working secret and all three passwords match the committed version; a reader with those values can impersonate an operator at a reachable hub, because [cookie roles are accepted using that secret](</Users/kaur/Documents/ChatGPT/Tower defence/manual-override/hub/__init__.py:624>). Fix: preserve local configuration, remove the real file from tracking, add a sanitized example, and rotate the secret/passwords during a stopped session, updating their consumers. If skipped: repository access remains sufficient to bypass the intended role boundary. Remote repository visibility and past disclosure were not established; removal from the current tree alone cannot revoke old credentials. No credential values are included in this report.

2. **A failed save can silently restore disabled modules on restart.** What this is: the hub persists enable/disable choices in [its settings methods](</Users/kaur/Documents/ChatGPT/Tower defence/manual-override/hub/__init__.py:238>). Problem: writes truncate the destination and suppress errors; malformed or unreadable settings become an empty disabled set, and the API still reports success after a write failure. A temporary-fixture reproduction returned HTTP 200 with `ok: true` after a simulated disk failure, then loaded no disabled modules; truncated JSON did the same. Fix: atomically replace validated settings, report write errors without publishing the new state or restarting, and distinguish first-run absence from corrupt existing data so startup can stop or mark modules unavailable. Apply the same preservation rule to [hub configuration loading/writing](</Users/kaur/Documents/ChatGPT/Tower defence/manual-override/hub/__init__.py:117>). If skipped: disabled modules can start again and saved configuration can be lost after an interrupted write.

**Should fix**

3. **Some legacy workers outlive their declared module lifecycle.** What this is: [Green Playfield Areas](</Users/kaur/Documents/ChatGPT/Tower defence/manual-override/sandboxes/green/prototypes/playfield-areas/prototype.py:444>) and its identical Purple copy own local area persistence; [Atom Manager](</Users/kaur/Documents/ChatGPT/Tower defence/manual-override/sandboxes/gamemaster/prototypes/atom-manager/prototype.py:620>) owns polling/discovery. Problem: both player Playfield modules start a never-ending saver at import, so even a disabled module starts work during discovery; area writes truncate files and swallow errors. Atom Manager starts workers in `hub_init` but has no `hub_stop` or stop condition. Fix: move starts into initialization, retain worker handles and a stop event, flush/join on shutdown, and use atomic writes with visible failure status. If skipped: disable/reload cannot reliably release owned resources, and interrupted writes can replace saved areas with defaults. Preserve separate team state when reusing implementation.

4. **Controller duplication already requires parallel maintenance.** What this is: the [5,861-line shared controller](</Users/kaur/Documents/ChatGPT/Tower defence/manual-override/shared/robot_controls/controller.html>) and [5,241-line Green Auto Pickup controller](</Users/kaur/Documents/ChatGPT/Tower defence/manual-override/sandboxes/green/prototypes/auto-pickup-game/controller.html>) share 5,039 matching lines. Problem: fixes to movement, calibration and cue recovery must be propagated to both; [an existing test explicitly reads both copies](</Users/kaur/Documents/ChatGPT/Tower defence/manual-override/tests/cal2_motion.test.js:24>). Purple also [serves files out of Green's module](</Users/kaur/Documents/ChatGPT/Tower defence/manual-override/sandboxes/purple/prototypes/auto-pickup-game/prototype.py:14>), so an independently imported Green setup can break Purple. Fix: reconcile the behavioral differences into the existing shared presentation owner, preserve each team's authenticated routes, and remove sibling-file reads. If skipped: fixes can diverge and team setup portability remains fragile.

5. **Two large pages have no serving route, and several served pages are identical copies.** What this is: Purple's local Auto Pickup controller is 1,622 lines, and Green's old calibration page is 1,132 lines. Problem: Purple's route serves Green's controller; the calibration route serves `calibrate2.html`, and no executable reference to `calibrate.html` was found. Other exact presentation duplicates include Cartesian, Joint Angles, Playfield, Pickup, Score and Cal 2 pages. Fix: verify the existing URLs with route tests, delete the two unserved pages, and share identical presentation through the established shared directory. If skipped: editors can fix an unused page or update only one copy. Do not treat the older Laser Tag Z engine as unused: it still has routes and is enabled in the current settings.

6. **Large runtime files mix unrelated reasons to change.** What this is: the main Photon engine is 4,865 lines, its legacy predecessor 4,516, the Y renderer 3,101, and the calibration/game owner 2,886. Problem: a change to enemy movement shares a class/file with ring topology, combat, placement and snapshot serialization; calibration session changes share a file with fitting, saved measurements, score logs and HTTP routes. Fix: extract cohesive internal responsibilities while keeping each module's state, locks, lifecycle and public contracts under the same owner. If skipped: each future change has a wider review and regression surface. The engines have 4,099 matching lines but distinct inputs/features; do not merge their mutable state or import one prototype's private implementation from the other.

7. **Tests and bundle assembly are tied to source layout.** What this is: several JS tests slice functions out of controller HTML using source strings, while both mobile adapters and [the exporter](</Users/kaur/Documents/ChatGPT/Tower defence/manual-override/tools/mobile-ltz/export.py:38>) assemble helper code separately. Problem: moving a function can break source-slicing tests without changing behavior, and the helper lists have already diverged: the live adapters prepend `connection-log.js`, the exporter does not, while `mobile.js` constructs `MobileConnectionLog`. The standard hosted PHP entry obtains the live bundle, so this is not evidence that the current hosted UI is broken. Fix: move behavioral tests to the extracted APIs, retain browser/route integration checks, and use one small pure bundle-assembly function for the existing consumers. If skipped: future extraction can publish incomplete bundles or leave tests checking textual boundaries rather than behavior.

**What is already working well.** The reviewed Photon and Mobile paths use named, versioned contracts, explicit unavailable states, team-scoped commands, server-owned game state and existing SSE delivery. The relay has targeted tests for ownership, calibration reservations, stale feedback, reconnection and Z limits. Plain Flask, Python and browser APIs fit the stated load. Keep these boundaries and safety checks. No runtime dependency was demonstrated to be removable, and this review found no measured production performance regression.

**How to keep files manageable**

- Treat 1,000 lines as an upper bound, not a target or reason to pad a file. Aim for roughly 400–800 lines in substantial modules so normal updates have room. Small cohesive helpers are valid.
- Count readable authored code, including HTML/CSS and tests. Minifying, removing useful comments or placing many statements on a line does not satisfy the goal. Several current short files contain multi-kilobyte lines, so count alone cannot measure maintainability.
- Add one small stdlib size-check script that covers the application and workspace tools/CAD/firmware. Warn above 800 and reject new maintained files above 1,000. During migration, record the existing 24 exceptions with their line counts; existing oversized files may shrink but not grow. Remove each exception when resolved. A final full check must have zero maintained-source exceptions.
- Exclude dependencies, generated bundles and historical output copies explicitly. Keep generated mobile/renderer bundles allowed to exceed 1,000 when all their authored inputs comply. Do not create a new abstraction or dependency merely to implement this check.
- Split around a named responsibility and a narrow callable interface. Keep locks, state ownership, persistence paths, public contracts and safety validation intact. Do not create generic `utils`, numbered file fragments, or a chain of inheritance layers merely to distribute line counts.
- Reuse the existing shared presentation directory for team-independent UI. Keep sandbox configuration and mutable team state local. Prototype implementation files stay within their owning module.
- Keep the current six-file mobile publication contract and frozen-build behavior. A small shared assembly function can concatenate authored helpers without widening deployed PHP/gateway allowlists or adding a frontend build framework.
